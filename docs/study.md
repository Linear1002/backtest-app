# 学習ガイド:このリポジトリを自分の言葉で説明できるようになるまで

Claude が書いた部分(データ層・Python リファレンス・API・画面・総当たり・買い持ち)を、**作者が面接で全部説明できる**ようになるための教材。
`docs/tour.md` が「どこに何があるか」の地図なら、このガイドは「どの順に、何を確かめながら読むか」の時間割。

- 1つの段階は 1〜3時間が目安。段階ごとに「読む → 手を動かす → 説明できるか確かめる」の3つをやる
- 確かめの問いの答えは、いちばん下の「答え」にある。**先に自分で答えを書いてから**見ること
- 分からない言葉は「用語」(終わりのほう)を見る
- 面接での話し方は `docs/interview.md`。このガイドは、その中身を本当に分かるためのもの

## 0. はじめに:全体を1枚で

```
画面(frontend/, Next.js)
  │  POST /api/backtests など(JSON)
  ▼
API(backend/, FastAPI)── 株価データ(backend/marketdata/:J-Quants・架空データ・Parquet)
  │  日足と条件を渡す
  ▼
計算エンジン(engine/reference/, Python の「正解」)── あとで C++ 版・CUDA 版(作者が書く)
```

いちばん大事な考え方は1つだけ:**「それらしい間違った数字」を出さない仕組みを、見た目より先に作った。**

1. 仕様(`docs/mvp.md`)に、計算の決まりを足し算の順番まで書いた
2. Python で、仕様と1対1で読める遅い「正解」を書いた
3. 正解データ(`tests/golden/`)を作り、C++ 版・CUDA 版はそれと一致させる
4. 画面では、良く見えすぎる数字に必ず注意を付ける(清算コスト控除前・生存者バイアス・試した数・買い持ちとの比較)

### 準備(最初に1回)

```bash

make dev-api                    # 別のターミナルで

```

## 段階1:仕様を読む(`docs/mvp.md`)

**目標**:コードを読む前に「何を計算するか」を自分の言葉で言えるようにする。

**読む**:`docs/mvp.md` の 2章(戦略)と 5章(指標)だけでよい。3章(データ)と 4章(画面)は流し読み。

**核心**

- **売買のタイミング**:当日の終値でシグナルを判定し、**次に売買が成立した日の始値**で約定する(2.6)。同じ日の終値で判定して同じ日の終値で買うと、「もう分かっている値段で買う」先読みになる
- **1日の処理の順番**(2.5):① 分割・併合 → ② 約定 → ③ 評価 → ④ シグナル判定。この順番を変えると答えが変わる
- **2種類の株価**(2.1):移動平均には「時点 t 基準の調整済み終値」、株数・お金には**未調整の株価**
- **クロスの判定**(2.3):割り算をしない `D(t) = S_short(t) × long − S_long(t) × short`。`D` の符号が −→+ なら買い、+→− なら売り

**確かめ**(答えは下)

- Q1-1. なぜ、データ提供元の「調整済み株価」をそのまま使わないのか
- Q1-2. なぜ、株数は調整済みではなく未調整の株価で決めるのか
- Q1-3. 移動平均を「割り算してから比べる」のではなく `D(t)` で比べるのはなぜか

## 段階7:総当たり(`docs/sweep.md`)

**目標**:「たくさん試すと、たまたま良いものを選んでしまう」ことと、それをこのアプリがどう見せているかを説明できる。

**読む**:`docs/sweep.md` → `engine/reference/sweep.py` → `backend/sweeps.py`(ジョブ)→ `backend/sweep_summary.py`(並べ方)→ `frontend/components/sweep/`

**核心**

- 1つ1つの組み合わせの計算は、1組のバックテストと**まったく同じ**(テストで一致を確かめている)
- **選ぶ期間と検証期間**:順位は選ぶ期間だけで付ける。検証期間は「確かめる」ためだけ。検証期間で良いものを選び直すと、検証期間も「選ぶ期間」になってしまう
- **選ぶ期間の始まりをそろえる**:データの初日から始めると、長期120日の組み合わせは最初の120日シグナルを出せない。条件がそろわないまま比べないよう、全部の組み合わせを同じ日から評価する
- **ジョブ**:計算に時間がかかるので、POST はすぐに返し、画面は途中経過を問い合わせる。Python のスレッドでは計算が並列にならない(GIL)ので、**プロセス**で並列にする
- **画面**:試した数・選ぶ期間の1位の検証期間での順位・順位相関(スピアマン)をいちばん上に出す。ヒートマップの色の物差しは選ぶ期間の値だけで決める(検証期間の情報を「選ぶ画面」に入れない)

**DEMO:1003 の既定の条件での結果**:105通り試して、選ぶ期間の1位(短期24日・長期30日)は、検証期間では **105通り中74位**。順位相関は **−0.17**。
「選ぶ期間で良かったものが、その先も良い」とはまったく言えない、ということが画面で分かる。

**手を動かす**:画面で総当たりを実行し、検証期間の開始日を「最後の2割」「最後の1年」に変えて、1位と順位相関がどう変わるかを表に書く。

**確かめ**

- Q7-1. 順位相関が −0.17 だった。何が言えて、何が言えないか
- Q7-2. 「1位のまわりも良い(なだらかな山)」なら、たまたまではないと言えるか
- Q7-3. ジョブをスレッドではなくプロセスで計算するのはなぜか

## 段階8:買い持ちとの比較(`docs/benchmark.md`)

**目標**:「この売買ルールに意味はあったか」を、比べる相手を使って説明できる。

**読む**:`docs/benchmark.md` → `engine/reference/benchmark.py`(短い)→ `backtest.py` の `fill_buy`・`apply_split_or_merger`(両方から呼ばれている)

**核心**

- 株価が上がった期間なら、下手な売買ルールでも利益は出る。だから、同じ期間・同じ費用で**ただ持ち続けた場合**と必ず並べる
- 買うタイミングは「最初の有効日の終値で決めて、次の有効日の始値で買う」。売買ルールと同じ決まりにそろえないと、買い持ちだけ1日早く買えて公平でない
- 約定・株数・分割の処理は、売買ルールと**同じ関数**を呼ぶ。そのうえで「1回だけ買って持ち続けた売買ルール」と資産額がビット単位で一致することをテストで確かめている
- 買えなかったとき(資金不足など)は比べない(値は初期資金のままで、現金と比べることになるため)

**DEMO:1003 の既定の条件**:移動平均クロス **+79.1%**、買い持ち **+178.0%**。代わりに最大ドローダウンは 22.2% と 41.0%。「リターンは負けたが、下がり方は小さかった」と数字で言える。

**確かめ**

- Q8-1. 買い持ちを「期間の初日の始値で買う」にすると、何が不公平になるか
- Q8-2. 配当を含めないことは、売買ルールと買い持ちのどちらに不利か

## 用語

| 用語 | 意味 |
|---|---|
| 有効日 | 終値がある日(売買が成立した日)。売買不成立の日はデータはあるが四本値が Null |
| ウォームアップ | 移動平均を作るためだけに使う、開始日より前のデータ。売買には使わない |
| 先読みバイアス | その時点ではまだ分からないはずの情報を使ってしまうこと |
| 生存者バイアス | 今も上場している銘柄しか選べないので、結果が良く見えやすいこと |
| 清算コスト控除前 | 最後の日に持っている株を、売る費用を引かずに評価した値 |
| スリッページ | 思った値段より不利な値段で約定すること。率で表す |
| 最大ドローダウン | それまでの最高値から、いちばん大きく減った割合 |
| シャープレシオ | 日次リターンの平均 ÷ 標準偏差 × √245。値動きの大きさの割にどれだけ増えたか |
| インサンプル / アウトオブサンプル | 選ぶのに使った期間 / 使っていない期間(このアプリでは「選ぶ期間」「検証期間」) |
| 過剰最適化 | 過去のデータにだけ合う組み合わせを選んでしまうこと(データスヌーピング) |
| スピアマンの順位相関 | 2つの順位がどれくらいそろっているか。1ならまったく同じ順、0なら関係なし、−1なら逆順 |
| 正解データ(ゴールデン) | リファレンスの答えをファイルに保存したもの。C++ 版はこれと答え合わせする |
| reducer | 「いまの状態」と「起きたこと」から「次の状態」を返す純粋な関数 |

## 答え

**段階1**

- Q1-1. 後で分割があると、データ提供元は**過去の値までさかのぼって書き換える**。その時点ではまだ分からない「将来の分割」の情報が、過去の移動平均に入ってしまう(先読み)。だから時点 t で分かる調整係数だけで、t ごとに計算し直す
- Q1-2. 調整済み株価は将来の分割で小さくなっているので、それで株数を決めると「本当はお金が足りなくて買えなかった取引」が成立してしまう
- Q1-3. 割り算は丸め誤差が出るので、短期線と長期線がほぼ同じ日に、実装によって判定が入れ替わる。掛け算だけの `D(t)` なら、C++ 版と同じ答えにしやすい

**段階2**

- Q2-1. 終値で判定した時点では、その日の取引はもう終わっている。次に注文できるのは次の日の寄付き。01-09 が売買不成立なら、注文を繰り越して、次の有効日の始値で約定する
- Q2-2. `cash / unit_cost / lot_size` の割り算の丸めで、ちょうど境目のとき lots が1多くなり、払う額が現金を少し超えることがある。そのときだけ1減らす
- Q2-3. 0.333… は2進数で正確に表せないので、300 ÷ 0.333… が 899.999… になり、切り捨てで899株になることがある。比率を 3/1 に戻し、整数の掛け算と割り算だけで計算すれば 900株になる
- Q2-4. Python の `round` は 0.5 を偶数に丸め(2.5 → 2)、C++ の `std::round` は 0 から遠い方に丸める(2.5 → 3)。どちらとも違う `floor(x + 0.5)` に決めておけば、両方の実装が同じ答えになる
- Q2-5. 標本(手元の日次リターン)から母集団のばらつきを見積もるので、不偏分散(N − 1 で割る)を使う。std = 0(毎日同じリターン、たとえば一度も売買しない)なら割れないので「算出不可」と出す

**段階3**

- Q3-1. 計算の途中で、未来のデータ(後の分割の係数や、後の日の株価)を使ってしまうバグ。正しく作っていれば、未来をどう書き換えても過去は変わらないはず
- Q3-2. 金額は足す順番やコンパイラの最適化で、最後の桁だけずれることがある(どちらも正しい)。株数や日付は整数・判定なので、1つでもずれたらその後の売買が全部変わる。だから完全一致
