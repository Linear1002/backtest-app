# 総当たり(パラメータの探索)の仕様

このドキュメントは、移動平均の日数の組み合わせを総当たりで試す機能の正とする。
1つの組み合わせの計算は `docs/mvp.md` とまったく同じで、ここではその「並べ方」と「選び方の見せ方」だけを決める。
計画の背景(なぜ総当たりか、GPU でどう速くするか)は `docs/gpu-plan.md`。

## 1. 目的と範囲

**ゴール**:1銘柄・1つの期間で、短期日数 × 長期日数の組み合わせをすべてバックテストし、成績をヒートマップと表で見られること。
あわせて、**選ぶのに使っていない期間(検証期間)での成績**と、**試した組み合わせの数**を必ず見せ、たまたま良かった組み合わせを選んでしまう危険(過剰最適化)を隠さないこと。

- 総当たりにするのは移動平均の日数(短期・長期)だけ。手数料率・スリッページ率・初期資金は全組み合わせで同じ
- 1銘柄だけ(複数銘柄は扱わない。`docs/mvp.md` 8章)
- 計算エンジン:Python リファレンス実装(複数のプロセスで並列に計算する)。C++ CPU 版・CUDA 版は、開発者が書いたあとで差し込む(`docs/gpu-plan.md` の G2〜G6)

## 2. 組み合わせ(格子)

| 入力 | 内容 |
|---|---|
| `short_min` `short_max` `short_step` | 短期日数の最小・最大・刻み |
| `long_min` `long_max` `long_step` | 長期日数の最小・最大・刻み |

- 短期日数の候補は `short_min, short_min + short_step, short_min + 2 × short_step, …` のうち `short_max` 以下のもの。長期も同じ
- 組み合わせは、短期 × 長期の候補のうち **短期 < 長期** のものすべて。短期 ≥ 長期の組は作らない(`docs/mvp.md` 4.3 で計算できない組だから)
- **組み合わせの順番**:短期の小さい順、短期が同じなら長期の小さい順。出力の行の順番と、エラーを報告する組み合わせの決め方(5章)に使う
- 例:短期 3〜30(刻み3)× 長期 20〜120(刻み10)は、短期10通り × 長期11通りのうち短期 < 長期の **105通り**(画面の既定値)

## 3. 期間の分け方(選ぶ期間と検証期間)

| 入力 | 内容 |
|---|---|
| `start` `end` | 期間(`docs/mvp.md` と同じ。休場日でもよい) |
| `holdout_start` | 検証期間の開始日。省略できる |

- `holdout_start` があるとき
  - **選ぶ期間**(インサンプル)= `start` 〜 `holdout_start` の前日
  - **検証期間**(アウトオブサンプル)= `holdout_start` 〜 `end`
- `holdout_start` がないときは、期間全体が選ぶ期間になり、検証期間はない
- **選ぶ期間の始まりをそろえる**:`start` より前の有効日が、組み合わせの中でいちばん長い長期日数 `L` 個に足りないときは、
  選ぶ期間の始まりを「それより前の有効日が `L` 個そろう最初の営業日」まで遅らせる。遅らせた分の日は、移動平均を作るため(ウォームアップ)にだけ使う
  - 理由:データの初日から始めると、長期の日数が長い組み合わせほど、選ぶ期間の初めにシグナルを出せない日が多くなる(`docs/mvp.md` 2.2)。
    その違いが順位に混ざらないように、**すべての組み合わせを同じ日から評価する**
  - 有効日だけを数える(売買不成立の日は数えない)。`start` より前の有効日が `L` 個以上あれば、`start` のまま
  - 例:データの初日から始め、長期の最大が120日なら、選ぶ期間は120個目の有効日の次の営業日から始まる
  - 検証期間は、その前に選ぶ期間(と遅らせた分の日)があるので、どの組み合わせもウォームアップがそろっている
- 組み合わせごとに、選ぶ期間と検証期間を**別々の**バックテストとして計算する
  - 検証期間のバックテストは、初期資金・持ち株なしから始める(選ぶ期間の持ち株を引き継がない)。「検証期間の初めから、この組み合わせを使い始めたら」という意味になる
  - 検証期間のウォームアップには、`holdout_start` より前のデータ(選ぶ期間のデータ)を使う。過去のデータなので先読みにはならない(`docs/mvp.md` 2.2)
- **選ぶのは選ぶ期間の成績だけで行う**。検証期間の成績は、選んだあとに「確かめる」ためだけに使う(7章)

## 4. 1つの組み合わせの計算

- 組み合わせ (短期, 長期) の1つの期間の計算は、`docs/mvp.md` のバックテストそのもの。パラメータは、その組の日数と、共通の手数料率・スリッページ率・初期資金・売買単位・年間の営業日数
- したがって、総当たりの1行は「同じ入力で1回だけバックテストした結果」の成績と、**完全に同じ値**になる(テストで確かめる)
- 出力するのは、期間ごとの成績(6章)だけ。日々の資産額や取引の記録は出さない(必要なら、その組み合わせで通常のバックテストをする)

## 5. チェックの順番

誤りが2つ以上あるとき、どれを報告するか(C++ 版・CUDA 版でも同じ順にする)。最初に見つかった誤りで止める。

1. **格子**(入力の誤り):`short_min` → `short_max` → `short_step` → `long_min` → `long_max` → `long_step` の順に、それぞれ「1以上の整数か」→「1000以下か」。
   次に `short_min ≤ short_max` → `long_min ≤ long_max` → 組み合わせが1つ以上あるか
2. **費用・資金**(入力の誤り):手数料率 → スリッページ率 → 初期資金 → 売買単位・年間の営業日数(`docs/mvp.md` 3.7 の1と同じ判定)
3. **期間**(入力の誤り):開始日 ≤ 終了日 → `holdout_start` があれば `start < holdout_start ≤ end`
4. **日付の順番**(データの異常):入力全体
5. **営業日の数**(入力の誤り):選ぶ期間の営業日が3日以上 → 検証期間があれば、その営業日が3日以上 →
   選ぶ期間の始まりをそろえたあと(3章)の選ぶ期間の営業日が3日以上
6. **レコード**(データの異常):**すべての組み合わせの読み込む範囲を合わせた範囲**の各レコード(`docs/mvp.md` 3.7 と同じ判定)。
   この範囲は、組み合わせの中でいちばん長い長期日数で「そろえた選ぶ期間の始まり〜`end`」を読み込むときの範囲(`docs/mvp.md` 2.2)に等しい。
   組み合わせによってエラーになったりならなかったりすると、成績を比べられないため、先にまとめて確かめる
7. **計算の途中**(データの異常):組み合わせの順番に計算し、株数が int64 に収まらない組み合わせが出たら、そこで止めて報告する

| 誤り | メッセージ |
|---|---|
| 日数・刻みが1未満・整数でない | 「日数と刻みは1以上の整数で入力してください」 |
| 日数・刻みが1000を超える | 「日数と刻みは1000以下で入力してください」 |
| 最小 > 最大 | 「短期の日数の範囲は、最小を最大以下にしてください」(長期も同じ) |
| 組み合わせがない | 「短期の日数が長期の日数より小さい組み合わせがありません。範囲を見直してください」 |
| `holdout_start` が範囲の外 | 「検証期間の開始日は、期間の開始日より後、終了日以前の日付にしてください」 |
| 選ぶ期間の営業日が3日未満 | 「選ぶ期間(検証期間より前)の営業日が3日未満です。検証期間の開始日を遅くしてください」 |
| 検証期間の営業日が3日未満 | 「検証期間の営業日が3日未満です。検証期間の開始日を早くしてください」 |
| そろえたあとの選ぶ期間が3営業日未満(検証期間あり) | 「長期の日数(最長L日)のウォームアップに使う日を除くと、選ぶ期間の営業日が3日未満になります。長期の日数を短くするか、検証期間の開始日を遅くしてください」 |
| そろえたあとの期間が3営業日未満(検証期間なし) | 「長期の日数(最長L日)のウォームアップに使う日を除くと、期間の営業日が3日未満になります。長期の日数を短くするか、期間を広げてください」 |

そのほか(期間・費用・資金・データ)のメッセージは `docs/mvp.md` 4.3 と同じ。

## 6. 出力:組み合わせごとの成績

組み合わせの順番に、選ぶ期間の行、続けて(検証期間があれば)検証期間の行を出す。

| 項目 | 内容 |
|---|---|
| `short_window` `long_window` | 組み合わせ |
| `segment` | `in_sample`(選ぶ期間)か `out_of_sample`(検証期間) |
| `total_return` `annualized_return` `max_drawdown` `sharpe_ratio` `win_rate` `trade_count` `winning_trades` `return_count` | `docs/mvp.md` 5章の成績表と同じ定義(算出不可・「−」は空欄) |
| `insufficient_cash_count` | 資金不足で約定しなかった回数 |
| `final_equity` | 期間の最終日の資産額(清算コスト控除前) |
| `holding_days` | 株を持っていた営業日の数(その日の評価のとき `shares > 0` だった日。`docs/mvp.md` 2.5 の手順3) |

**一致の基準**(C++ 版・CUDA 版):`trade_count` `winning_trades` `return_count` `insufficient_cash_count` `holding_days` `win_rate` と行の並び(組み合わせ・`segment`)は完全に一致。
それ以外の小数は `|a − b| ≤ 1e-12 + 1e-9 × |b|`(`docs/mvp.md` 6章と同じ)。

## 7. 並べ方とまとめ(API が行う。エンジンは行わない)

**並べる基準**(画面で選ぶ)

| 基準 | よい順 |
|---|---|
| シャープレシオ(既定) | 大きい順 |
| 総リターン | 大きい順 |
| 最大ドローダウン | 小さい順 |

- 算出不可の値は最後。値が同じなら組み合わせの順番(表の並びを決めるためだけ。順位は同じ値なら同じ)
- **順位は選ぶ期間の成績だけで決める**
- **順位**はどちらの期間も同じ決め方:`1 +`(その期間の基準の値がそれより良い組み合わせの数)。同じ値なら同じ順位。
  算出不可の組み合わせには順位を付けない。「N通り中 M位」の N は、その期間で値がある組み合わせの数

**まとめ**

| 項目 | 定義 |
|---|---|
| 試した数 | 組み合わせの数 |
| 選ぶ期間の1位 | 上の基準で1位の組み合わせと、その成績。**1位と同じ値の組み合わせが2つ以上あるとき(同率1位)は、1位を1つに決めない**(その数を出す。例:全部の組み合わせが一度も株を持たず、総リターン・最大ドローダウンがすべて0) |
| 1位の検証期間の成績 | 1位の組み合わせの、検証期間の成績 |
| 1位の検証期間での順位 | 上の順位の決め方で、1位の組み合わせの検証期間での順位。値が算出不可か、同率1位なら出さない |
| 順位の相関 | 選ぶ期間と検証期間の、基準の値の順位相関(スピアマン。同じ値は平均の順位)と、計算に使った組み合わせの数。両方の値がある組み合わせが3つ以上で、どちらの値もすべて同じでないときだけ。**読み方の目安(「ほとんど関係がない」など)は、組み合わせが10以上のときだけ出す** |
| 1位の周りの平均 | 格子で1位のとなり(短期・長期それぞれ1刻み前後、最大8つ)の組み合わせの、選ぶ期間の基準の値の平均。値がある組み合わせだけ。同率1位なら出さない |
| 株を持っていた日 | 1位の組み合わせが株を持っていた営業日の数(`holding_days`)。0なら「一度も株を持っていない」と書く(最大ドローダウンで並べると、売買の少ない組み合わせほど上に来るため) |
| 買い持ち(比較) | 期間ごとの買い持ち(`docs/benchmark.md`)の成績。選ぶ期間・検証期間それぞれ、その期間の最初から計算する |
| 買い持ちより良かった数 | 期間ごとに、基準の値が買い持ちより良かった組み合わせの数(同じ値は数えない。買い持ちの値が算出不可なら出さない)。「N通り中 M通り」の N は順位と同じく、値がある組み合わせの数 |

- となりの組み合わせは日数が少し違うだけで、ほとんど同じ売買をする。そのため、順位相関に使った組み合わせの数ほどの、独立した証拠にはならない。
  画面では、数と読み方の目安を並べて出し、「目安」とはっきり書く

## 8. 画面に必ず出すこと(過剰最適化への備え)

- **試した数**:「105通りの中で最も良い組み合わせ」と書く。1つだけ試した結果とは意味が違う。
  条件(格子・期間・検証期間の開始日・並べる基準)を変えて試し直した分も、本当は試した数に入ることを書く
- **検証期間の成績**を、選ぶ期間の成績と並べて出す。検証期間がないときは、ないことと、その危うさを書く
- **検証期間で選び直さない**:検証期間の成績で並べ替えて選ぶと、検証期間も「選ぶ期間」になってしまう。画面では、並べ替えは選ぶ期間でしかできない。
  検証期間のヒートマップを出すときは「確かめるためのもの」と書く
- **検証期間の短さ**:検証期間の営業日の数から、シャープレシオが偶然だけでどれくらいぶれるか(年率に直した標準誤差の目安 `√(年間の営業日数 / (営業日数 − 1))`)を書く
- **ヒートマップで「山」の形を見る**:1位のまわりも良い(なだらかな山)なら、日数を少し変えても成績が崩れにくいことは分かる。
  ただし、となりの組み合わせはほとんど同じ売買をするので、たまたまではない証拠にはならない。1マスだけ飛び抜けているなら疑う
- **ヒートマップの色の物差しは、選ぶ期間の値だけで決める**(いちばん大きい絶対値を端の色にする)。検証期間の値で決めると、検証期間の情報が「選ぶ画面」に入ってしまうため。
  検証期間のヒートマップも同じ物差しで塗り、物差しを超える値は端の色にする(数字は読み取り欄と表で読める)
- **選ぶ期間の始まりをそろえたとき**(3章)は、何日をウォームアップにだけ使ったかを書く(日数は有効日の数。`docs/mvp.md` 4.1 のウォームアップの営業日数と同じ数え方)
- **買い持ちと比べる**:1位の検証期間の成績が、同じ期間の買い持ちより良かったか悪かったかを書く。ヒートマップの色の物差しにも、買い持ちの値の位置を出す。
  検証期間で買い持ちを上回った組み合わせの数は、1位がたまたまかを見るためのもので、上回った組み合わせを選び直すためのものではない
- MVP の注意書き(清算コスト控除前・生存者バイアス・架空データ・約定の前提)は、総当たりにもそのまま当てはまる

## 9. 上限

| エンジン | 組み合わせの上限 |
|---|---|
| Python リファレンス実装 | 2,000通り |
| C++ CPU 版・CUDA 版(できたら) | 20,000通り |

- 上限は API が確かめる(エンジンは確かめない)。メッセージ:「組み合わせが多すぎます(N通り)。このエンジンでは M通りまでです。範囲を狭めるか、刻みを大きくしてください」
- Python で 2,000通り × 2期間を計算すると、1つのコアで数分かかる(1回の計算は数十ミリ秒。長期日数が長いほど遅い)。API は CPU のコアの数だけプロセスを使って並列に計算し、途中経過を返す(10章)

## 10. API

```
POST   /api/sweeps        総当たりを始める → 202 と、ジョブの id
GET    /api/sweeps/{id}   途中経過(終わった数 / 全体の数)。終わったら結果
DELETE /api/sweeps/{id}   中止する
```

- 計算に時間がかかるので、リクエストはすぐに返し、画面は途中経過を問い合わせる(ジョブ)。中止もできる
- ジョブは API サーバーのメモリにだけ持つ(再起動すると消える。ローカルで1人が使う前提)。終わったジョブは30分で消す
- 入力チェック(5章の1〜6と、9章の上限)は `POST` の時点で行い、誤りがあれば 422 を返す。7(計算の途中)の誤りは、ジョブの失敗として返す

## 11. 答え合わせのファイル(C++ 版・CUDA 版のため)

単体のバックテスト(`docs/cpp/contract.md`)と同じ考え方で、ファイル同士で答え合わせする。

```bash
build/engine/cpp/sweep_cli 入力フォルダ 出力フォルダ
uv run python -m engine.reference.sweep_cli 入力フォルダ 出力フォルダ   # リファレンス
```

**入力**:`bars.csv`(`docs/cpp/contract.md` と同じ)と `sweep.txt`

```
start=2022-01-04
end=2026-07-31
holdout_start=2025-08-01
short_min=3
short_max=12
short_step=3
long_min=15
long_max=45
long_step=10
fee_rate=0.001
slippage_rate=0.0005
initial_cash=1000000.0
lot_size=100
trading_days_per_year=245
```

`holdout_start=` が空欄なら、検証期間なし。率は割合(0.1% は `0.001`)。

**出力**:`combos.csv`(6章の列。この順)

```
short_window,long_window,segment,total_return,annualized_return,max_drawdown,sharpe_ratio,win_rate,trade_count,winning_trades,return_count,insufficient_cash_count,final_equity,holding_days
```

エラーのときは `error.txt` だけ(`kind=input` か `kind=data`)。終了コードは単体のバックテストと同じ(0 / 2 / それ以外)。
単体のバックテストと同じく、答え合わせで比べるのは `kind` だけ(`message` は自由)。そのため、同じ種類の誤り同士の順番(5章)は、
ファイルの答え合わせでは確かめられない。入力とデータの誤りの順番(`se07`・`se08`)と、API のテストで確かめる。

**正解データ**:`tests/golden/sweeps/`(`manifest.json` にケースの一覧)。`make test-cpp` が、`sweep_cli` があれば比べる。

## 12. 既知の限界

- `docs/mvp.md` 7章の簡略化は、すべての組み合わせにそのまま当てはまる
- 検証期間を1つに分けるだけ(ウォークフォワード:選ぶ期間と検証期間を少しずつずらして繰り返す、はまだない)
- 試した数を考えに入れてシャープレシオを割り引く方法(Deflated Sharpe Ratio など)は、まだ入れていない。画面では「試した数」と検証期間の成績で代わりに注意を促す
- 試した数は、その1回の実行の組み合わせの数だけ。画面で何度も試し直した回数は数えていない(注記で知らせるだけ)
- 1銘柄だけ。複数の銘柄で同じ組み合わせが良いかは確かめていない
