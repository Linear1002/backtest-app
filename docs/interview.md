# 面接で話せること

このプロジェクトを、就活・院試の面接で説明するためのメモ。台本ではなく「話の材料」。
自分の言葉で話せるように、それぞれ「なぜそうしたか」を自分で説明できるか確かめておく(最後のチェックリスト)。

## 1. 30秒で

> 日本株のバックテストを日本語の画面で実行できる Web アプリを作っています。
> 特にこだわったのは「結果が正しいこと」で、先読みバイアスが入らないように、株式分割の調整もその日までに分かる情報だけで行っています。
> 計算エンジンは、仕様どおりに書いた Python 版を「正解」にして、自分で書く C++ 版が 60 個の正解データと一致するかを、CI で自動で確かめる仕組みにしています。
> パラメータの総当たりも、画面と Python 版はできていて、次はそれを CUDA で並列にして速くするところに取り組みます。

## 2. 2分で(構成と流れ)

- **画面**(Next.js):銘柄 → 戦略 → 条件 → 確認 → 結果 の5段階。結果は損益グラフ・成績表・取引の記録
- **API**(FastAPI):入力のチェック、データの取得、計算エンジンの呼び出し
- **データ**:J-Quants API(東証)と、公開デモ用の架空データ。Parquet で保存
- **計算エンジン**:Python リファレンス実装(正解)と C++ 版(自分で書く)。pybind11 でつなぎ、画面から切り替えられる
- **品質**:pytest・GoogleTest・node:test・Playwright(画面〜API の通しのテストと、アクセシビリティの自動チェック)・CI(GitHub Actions)。
  仕様書(`docs/mvp.md`)を先に書き、実装とテストは仕様の節番号で対応させた

## 3. 技術的にこだわったところ(深掘りされたら)

### 3.1 先読みバイアスを「仕組み」で防ぐ

- シグナルは当日の終値で判定し、**次に売買が成立した日(有効日)の始値**で約定する(当日の終値で判定して当日の終値で買うのは、現実にはできない)
- 移動平均には「時点 t 基準の調整済み終値」を使う。**J-Quants が返す調整済み株価は使わない**
  - 理由:調整済み株価は、新しい株式分割があると過去の値までさかのぼって書き換わる。そのまま使うと、t の時点では知らないはずの将来の分割の情報が入る
  - 代わりに、未調整の終値と調整係数を保存し、t ごとに「t までに起きた分割だけ」で調整し直す
- **株数・資金の判定には未調整の株価を使う**。調整済み株価で「買えたかどうか」を判定すると、将来の分割で過去の株価が下がり、本当は資金不足で買えなかった取引が成立してしまう(独立した検証で見つかり、仕様を直した)
- ウォームアップ:開始日より前のデータで移動平均を作っておく(過去のデータなので先読みにはならない)

### 3.2 分割比率を分数に戻す

- 調整係数は 1:3 の分割で 0.333333 のような近似値。そのまま割り算して切り捨てると持ち株数が1株ずれる
- 係数から p/q(q ≤ 1000)に戻して、**株数は整数だけで計算**する。丸めは `floor(x + 0.5)` に決めた(Python の `round` は偶数への丸め、C++ の `std::round` は 0 から遠い方への丸めで、言語によって結果が違うため)

### 3.3 Python と C++ の結果を一致させる(ビット単位まで)

- 浮動小数点は、足す順番が変わるだけで結果が変わる。仕様に「古い日から順に1つずつ足す」と計算の順番まで書いた
- コンパイラが掛け算と足し算を1つの命令(FMA)にまとめると丸めが変わるので、`-ffp-contract=off` を付け、`-ffast-math` は使わない
- 一致の基準を2つに分けた:シグナルの日付・株数・勝ち負けなどは**完全一致**、資産額などの小数は**許容誤差**(`1e-12 + 1e-9 × |値|`)。
  さらに厳しく、小数まで完全一致で比べるモード(`BACKTEST_CPP_STRICT=1`)も用意した。これに通れば「ビット単位で一致」と言える
- 正解データ(ゴールデンケース)は60個:手で作った境界ケース26個(同値をはさんだクロス、資金不足、売買不成立の日の権利落ち、
  損益が +ε で計算の順番を変えると勝ち負けが入れ替わる取引 など)、架空銘柄の実際の流れ13個、エラーのケース19個、
  切り出していない入力(API と同じく全期間を渡す)2個
- ケースごとに「どのマイルストーンで合格するか」を決めてあり、C++ を段階的に書きながら答え合わせできる(`docs/cpp/README.md`)

### 3.4 数字を正直に見せる

- 手数料・スリッページのデフォルトを 0 にしない(0 だと実際より良く見える)
- 期間の最後に持っている株は売らずに評価し、「清算コスト控除前」と明記する
- 生存者バイアス(今も上場している銘柄しか選べない)を結果画面に書く
- 年率リターンは、期間が1年未満なら「参考値」と書く

### 3.5 データの利用規約を守る設計

- J-Quants の無料プランは私的使用のみ。データは Git に入れず、公開デモには架空データを使う
- データの取得部分は「データソース」というインターフェースの裏に隠したので、商用データに替えるときは1クラス足すだけ
- 無料プランは1分間に5回まで。直近60秒の回数を数えて自動で待つ(429 が返ったら、公式の推奨どおり2分待つ)

### 3.6 総当たりで「たまたま」を選ばない(`docs/sweep.md`)

- 移動平均の日数の組み合わせ(既定 105通り)をすべて試し、ヒートマップで比べる。1つ1つの計算は1組のバックテストとまったく同じ(テストで一致を確かめている)
- たくさん試すほど、**偶然うまくいっただけの組み合わせ**が1位に来る(データスヌーピング・過剰最適化)。そこで:
  - 期間の最後を**検証期間(アウトオブサンプル)**として取っておき、選ぶのには使わない。順位は選ぶ期間だけで付ける
  - 画面のいちばん上に「何通り試したか」「選ぶ期間の1位が、検証期間では何位だったか」「選ぶ期間と検証期間の順位相関」を出す
  - 架空データ DEMO:1003 を既定の条件(105通り・期間の最後の3割が検証期間)で試すと、選ぶ期間の1位(短期24日・長期30日、シャープレシオ 1.71)は
    検証期間では 0.83 で 105通り中 74位、順位相関は −0.17 だった。**選ぶ期間の成績は、この先の成績をほとんど予想できていない**ことが画面で分かる
    (この数字は通しのテスト `frontend/e2e/backtest.spec.ts` で確かめているので、ずれたらテストが落ちる)
  - 検証期間は約1.4年(337営業日)。この長さだと、シャープレシオは偶然だけでも ±0.9 くらいぶれる(標準誤差の目安 √(245 / 336))。それも画面に出す
- **比べる条件をそろえる**:長期120日の組み合わせは、最初の120営業日は移動平均が作れずシグナルを出せない。短い組み合わせと評価する日がずれると、
  日数の違いではなく「評価した期間の違い」が順位に混ざる。そこで、選ぶ期間の始まりを、いちばん長い長期日数のウォームアップがそろう日にそろえた
  (独立した検証役の指摘で直した。`docs/sweep.md` 3章)
- 色の物差しも選ぶ期間の値だけで決める。検証期間の値で決めると、「選ぶ画面」の色の濃さに検証期間の情報が入り込む
- 計算は時間がかかるので、API はジョブにして途中経過を返し、CPU のコアの数のプロセスで並列に計算する。ここを C++・CUDA に置き換えるのが次の段階

## 4. 聞かれそうな質問と、答えの方向性

| 質問 | 答えの方向性 |
|---|---|
| 先読みバイアスはどう防ぎましたか | 3.1。約定のタイミング、時点 t 基準の調整、未調整株価での株数の判定 |
| なぜ調整済み株価をそのまま使わないのですか | 過去にさかのぼって書き換わるから。時点 t で知り得た値ではない |
| このバックテストの限界は何ですか | `docs/mvp.md` 7章。寄付きで必ず約定する仮定、ストップ高・安、配当・税金なし、生存者バイアス。**限界を自分から言えることが大事** |
| 移動平均クロスで儲かりますか | 正直に「この期間・この銘柄ではこうだった」以上のことは言えない。過剰最適化の話につなげる(`docs/gpu-plan.md` 4章) |
| パラメータを総当たりにしたら、何が問題になりますか | データスヌーピング。試した数の表示、アウトオブサンプル(このアプリでは実装済み。3.6)、ウォークフォワード・Deflated Sharpe Ratio(まだ) |
| 検証期間で良かった組み合わせを選べばいいのでは | それをすると検証期間も「選ぶ期間」になり、確かめたことにならない。だから画面でも並べ替えは選ぶ期間でしかできない |
| シャープレシオの年率換算の √245 は何の仮定ですか | 日次リターンが独立で同じ分布という仮定。自己相関があるとずれる |
| C++ と Python で結果が合わなかったら、どう調べますか | ゴールデンケースで最初に違う行を探し、その日の値を手順(分割→約定→評価→シグナル)ごとに比べる |
| GPU で何を並列にしますか | パラメータの組み合わせごと。移動平均の和の表は組み合わせ間で使い回せる(`docs/gpu-plan.md` 3章) |
| GPU で倍精度を使うと遅くないですか | ゲーム向け GPU は倍精度が単精度の 1/64。正しさと速さの両立の工夫(2段階方式など)を話す |
| テストはどう書きましたか | 仕様の節ごとの単体テスト、境界ケース、「未来のデータを書き換えても過去のシグナルが変わらない」性質のテスト、ゴールデンケース、画面と API で同じ表を読む入力チェックのテスト、画面〜API の通しのテスト、CI |

## 5. AI(Claude Code)と一緒に作ったことの話し方

このプロジェクトは Claude Code と分担して作っている。**分担は正直に話す**(隠すと、深掘りされたときに答えられない)。

| 部分 | 誰が | 自分の役割 |
|---|---|---|
| 仕様(`docs/mvp.md`) | 一緒に | 何を作るか・どこまでやるかを決め、検証部(quant-validator)の指摘をどう直すかを判断した |
| 画面・API・データ層・Python リファレンス | Claude Code | 計画を承認し、レビューし、コードの読み方を理解した(`docs/tour.md`) |
| **C++ 版エンジン・CUDA 版** | **自分** | 仕様からゼロから書き、正解データと一致させる(いまは書いている途中。下の注意) |
| 検証の仕組み | 一緒に | 独立したレビュー役(検証部・レビュー部)を置き、指摘を直す流れを作った |

話し方の例:「AI に書かせた部分も、仕様と照らしてレビューし、説明できるようにしてあります。計算の中心の C++ は自分で書いて、AI が書いた Python 版と、60 個の正解データで一致させました。AI の出力をそのまま信じずに検証する仕組みを作ったことも、このプロジェクトで学んだことです」
**注意:この話し方は、C++ 版が完成してから使う**。いま言えるのは「C++ 版を書いている途中で、いまは M◯ まで正解データと一致している」まで。
「一致させました」と言うのは `make test-cpp`(M5 以上)が通ってから、「ビット単位で一致」と言うのは `BACKTEST_CPP_STRICT=1 make test-cpp` が通ってから。
CUDA 版も同じで、書く前に「GPU で速くした」とは言わない(計画は `docs/gpu-plan.md`)。
