# MVP仕様

このドキュメントはMVPの範囲・戦略・指標の定義の正とする。
実装(Pythonリファレンス・C++・CUDA)とテストは、ここに書かれた定義に従う。

## 1. 目的と範囲

**ゴール**:東証上場の1銘柄に対して、移動平均クロス戦略のバックテストを画面から実行し、損益グラフと成績表を確認できること。

**MVPに入れないもの**

- 複数銘柄の同時実行
- GPU版(CUDA)。MVPはCPUで計算する
- ログイン・認証
- 課金
- 公開デプロイ(ローカル環境でのみ動かす。理由は「3. データ」の利用規約を参照)

## 2. 戦略:移動平均クロス

### 2.1 用語と使う価格

- **営業日**:その銘柄のデータにレコードがある日(3.4)。
- **有効日**:営業日のうち、終値がNullでない日。売買不成立の日は、四本値がすべてNullになる(3.1)。
- **期間内の営業日**:開始日以上・終了日以下の営業日。開始日・終了日が休場日でもよい。
- 価格は用途によって使い分ける。

| 用途 | 使う価格 |
|---|---|
| シグナル判定(移動平均) | 時点 t 基準の調整済み終値(2.2) |
| 株数・資金・約定・評価額 | 未調整の株価(その日に実際に付いた価格) |

調整済み株価で株数や資金不足を判定すると、t より後の分割の情報が、売買するかどうかに入り込んでしまう(先読み)。このため、売買には未調整の株価を使う。

### 2.2 移動平均

**時点 t 基準の調整済み終値**

時点 t で知り得る調整係数だけを使って、過去の終値を調整する。s ≤ t の営業日 s について、次のように定める。

```
CumAdj_t(t) = 1
CumAdj_t(s) = CumAdj_t(s+1) × AdjFactor(s+1)   (s+1 は s の次の営業日。t から過去へ順に掛けていく)
P_t(s)      = C(s) × CumAdj_t(s)                (C は未調整の終値)
```

- `AdjFactor` は権利落ち日のレコードに入る値(1:2の分割なら0.5)。分割・併合だけでなく、株主割当増資(`ExRT = 3`)の係数も含めて使う。
- 計算の途中で丸めない。J-Quantsが返す調整済み株価(`AdjC` など)は使わない(3.1)。
- `P_t(s)` は必ず `C(s) × CumAdj_t(s)` の形で、t ごとに計算する。前の日の調整済み系列に係数を掛け直すなど、途中の結果を使い回す計算はしない。掛ける順番が変わると丸め誤差が変わり、2.3の判定が実装によってずれるため。

**単純移動平均(SMA)**

- `window` 日の移動平均は、t 以前の直近 `window` 個の有効日 s について、`P_t(s)` を平均した値。
- 和 `S_window(t)` は、古い日から新しい日の順に1つずつ足す。
- 有効日が `window` 個そろっていない日は、SMAを**未定義**とする。短期線にも長期線にも同じルールを使う。
- 終値がNullの日(有効日でない日)には、SMAを計算しない。
- 数値はすべて float64 で扱う。

**ウォームアップ期間**

- 開始日より前のデータがあれば、それも移動平均の計算に使う。開始日のシグナル判定には、直前の有効日の長期線が必要になる。そのため、開始日より前の有効日 `long_window` 個分をウォームアップ期間として読み込む。
- ウォームアップ期間のデータは、移動平均の計算にだけ使う。この期間にはシグナルを判定せず、約定もせず、資産額や指標にも含めない。
- 開始日より前のデータが `long_window` 個に足りないときは、あるだけを使う。その結果SMAが未定義になる日は、シグナルを出さない。
- 読み込む範囲は、ウォームアップの最も古い有効日から終了日までの**すべての営業日のレコード**とする。売買不成立の日も読み込む。権利落ち日が売買不成立の日と重なっても、その日の `AdjFactor` が抜け落ちないようにするため。

### 2.3 クロスの判定

丸め誤差を減らすため、割り算をせずに比べる。

```
D(t) = S_short(t) × long_window − S_long(t) × short_window
```

D(t) > 0 は「短期線 > 長期線」と同じ意味。t' を t の直前の有効日とする(ウォームアップ期間の日でもよい)。

`D(t')` には、**t' の日に t' 基準(`P_{t'}`)で計算した値**を使う。t の日に t 基準で計算し直さない。数学的には符号が同じでも、権利落ち日には丸め方が変わり、`D = 0` 付近で判定が変わることがあるため。

| シグナル | 条件 |
|---|---|
| 上抜け(買い) | `D(t') ≤ 0` かつ `D(t) > 0` |
| 下抜け(売り) | `D(t') ≥ 0` かつ `D(t) < 0` |

- シグナルを判定するのは、期間内の有効日 t のうち、t と t' の両方で短期線・長期線が定義されている日だけ。
- `D(t) = 0`(当日の短期線と長期線が同じ値)のときは、クロスとみなさない。
- **接するだけでもシグナルになる**:短期線が長期線の「上 → 同値 → 上」と動くと、3日目は `D(t') = 0` かつ `D(t) > 0` なので上抜けになる。「下 → 同値 → 下」も同じく下抜けになる。これは定義どおりの動きとする。
- 判定に使うのは、時点 t までの終値と調整係数だけ。t より後のデータは使わない(先読みバイアスの禁止)。

### 2.4 売買ルール

- **買いのみ(ロングオンリー)**。空売りはしない。
- 持っている株がないときに上抜けが出たら、買う。
- 持っている株があるときに下抜けが出たら、全株を売ってノーポジションにする。
- それ以外のシグナル(持ち株があるときの上抜け、持ち株がないときの下抜け)は無視する。

### 2.5 1日の処理の順番

期間内の営業日 t ごとに、次の順で処理する。

1. **分割・併合の処理**:t が分割・併合の権利落ち日で、株を持っていれば、持ち株数を変える(2.8)。
2. **約定**:前の有効日に出たシグナルの注文があれば、t の始値で約定する(2.6)。t の始値がNullなら、次の有効日に繰り越す。
3. **評価**:t の資産額 `equity(t)` を計算する(5章)。
4. **シグナル判定**:t が有効日なら、クロスを判定する(2.3)。シグナルが出たら、次の有効日に約定する注文として持つ。

始値と終値はいっしょにNullになる(3.1)。そのため、繰り越した注文は必ず次の有効日の手順2で約定し、その日の手順4より前に片づく。注文が2つ以上たまることはない。

### 2.6 約定

- **当日の終値でシグナルを判定し、次の有効日の始値で約定する。**
- 期間の最終日に出たシグナルや、期間の最後まで約定できなかった注文は、約定しない。
- 約定価格(スリッページ込み、`O` は未調整の始値)
  - 買い:`fill_price = O(約定日) × (1 + slippage_rate)`
  - 売り:`fill_price = O(約定日) × (1 − slippage_rate)`
- 約定代金:`notional = fill_price × shares`
- 手数料:`fee = notional × fee_rate`(約定ごと。最低手数料は設けない)
- 買いのときは `buy_cost = unit_cost × shares`(2.7)を現金から引く。数学的には `notional + fee` と同じだが、株数の判定と同じ式にそろえるため、この形で計算する。
- 売りのときは `notional − fee` を現金に足す。
- 金額は丸めず、float64 で扱う。株数は64ビット整数。

### 2.7 株数の決め方

- 手持ちの現金で買える最大の株数を、売買単位(東証は100株)の倍数で買う。株数は約定日の始値(未調整)で決める。これは理想化であり、7章に書く。
- 計算の順番は次のとおりに固定する。

```
unit_cost = fill_price × (1 + fee_rate)
lots      = floor(cash / unit_cost / lot_size)
shares    = lots × lot_size
もし unit_cost × shares > cash なら、lots を1減らして shares を計算し直す(1回だけ)
```

- 最後の行は、割り算の丸めで `lots` が1多くなる境目のケースのためのもの。
- `shares` が0(100株分の資金に足りない)のときは買わずにスキップし、「資金不足で約定しなかった回数」に1を足す。スキップした後も、ノーポジションのまま次のシグナルを待つ。
- 買った後の現金が負になったら、実装のバグとしてエラーにする(アサート)。上の手順に従えば、正しい計算では負にならない。C++ では `assert` マクロを使わない(既定の Release ビルドでは `NDEBUG` で消えるため)。Release でも止まる形(例外を投げて、終了コードを 0・2 以外にする)にする。

### 2.8 分割・併合の処理

- 権利落ちの種類が分割・併合(`ExRT` が 1 または 2)で、`AdjFactor` が 1 でない日 t に株を持っていたら、持ち株数を変える。端数の換金(下記)を除き、現金は変えない。`AdjFactor` が 1 の日は、`ExRT` があっても何もしない。
- `AdjFactor` は小数(1:3の分割なら0.333…)なので、そのまま割り算して切り捨てると株数が1株ずれることがある。このため、まず比率を分数に戻し、株数は整数だけで計算する。

```
ratio = 1 / AdjFactor(t)
q = 1, 2, …, 1000 のそれぞれについて p = round(ratio × q) とし、   ← round は floor(ratio × q + 0.5)(0.5 は切り上げ)
|p / q − ratio| が最小になる (p, q) を選ぶ(同じなら q が小さいほう)
new_shares = floor(shares × p / q)        ← 整数の掛け算と割り算で計算する
fraction   = (shares × p mod q) / q       ← 1株未満の端数(株数)
```

- `round` は `floor(x + 0.5)` に決める。Python の `round()` は 0.5 を偶数に丸め(2.5 → 2)、C++ の `std::round()` は 0 から遠い方に丸める(2.5 → 3)ため、どちらも使わない。
- 例:1:2の分割は `AdjFactor = 0.5` → `p/q = 2/1` で2倍。2:3の分割は `p/q = 3/2`。10:1の併合は `AdjFactor = 10` → `p/q = 1/10`。
- 選んだ `p/q` と `ratio` の相対誤差 `|p/q − ratio| / ratio` が 1e-4 を超えるときは、想定外の係数としてエラーにする。
- 扱う比率は1000倍までとする(`AdjFactor` が 0.001〜1000)。範囲の外はエラーにする(3.7)。
- 整数の掛け算 `shares × p` は C++ では `int64_t` で行う。この値が `int64_t` の範囲を超えるときは、どちらの実装もエラーにする。
- 端数 `fraction` が出たときは、その日の評価価格(5章)で現金に換える:`fraction_cash = fraction × 評価価格(t)`。手数料・スリッページはかけない(7章)。
- 併合で `new_shares` が0になったときは、その日に決済したものとして扱う。取引回数と勝率に含め、1往復の損益は端数を現金に換えた額で計算する(5章)。 その日に約定待ちの売り注文があれば、売る株がないので取り消す。
- 株主割当増資(`ExRT = 3`)では、持ち株数を変えない(7章)。
- データの異常(`AdjFactor` が Null、`AdjFactor ≠ 1` なのに `ExRT` が Null か1〜3以外、分数に戻せない係数 など)のチェックは 3.7 にまとめた。持ち株があるかどうかに関係なくチェックする。

### 2.9 期間の最後に持っている株

- 最終日の評価価格で評価額を計算するだけで、売却はしない。
- この未決済の取引は、取引回数と勝率に含めない。
- そのため、最終日の資産額は売りの手数料・スリッページを引く前の値になる。結果画面に「清算コスト控除前」と注記する。

## 3. データ

### 3.1 データソース(MVP):J-Quants API Free

| 項目 | 内容 |
|---|---|
| 対象 | 東証上場株・日足 |
| 期間 | 約2年分 |
| 遅延 | 12週間 |
| API | V2(`GET https://api.jquants.com/v2/equities/bars/daily`)。APIキーを `x-api-key` ヘッダーで渡す。`code` と `from`/`to` で銘柄と期間を指定し、続きがあるときは `pagination_key` が返る |
| 利用規約 | **私的使用のみ** |

**使うフィールド**(公式仕様 https://jpx-jquants.com/en/spec/eq-bars-daily で確認済み)

| フィールド | 内容 |
|---|---|
| `Date` | 日付(YYYY-MM-DD) |
| `Code` | 銘柄コード(例:`"86970"`) |
| `O` / `H` / `L` / `C` | 未調整の始値・高値・安値・終値(円)。後から変更されない |
| `Vo` | 未調整の出来高 |
| `AdjFactor` | 調整係数。権利落ち日のレコードに入る(1:2の分割なら0.5)。それ以外の日は1 |
| `ExRT` | 権利落ちの種類(1:分割、2:併合、3:株主割当増資)。該当しない日はNull |

公式仕様に書かれていることのうち、この仕様に関わるもの:

- **売買不成立の日**:売買不成立や終日売買停止の日でも、上場期間内ならレコードは返る。四本値・出来高・売買代金がすべてNullになり、一部だけがNullになることはない。
- **調整済み株価(`AdjO` など)**:小数第1位に丸めて返される。新しい分割などがあると、過去の分までさかのぼって計算し直される。そのため、この仕様では使わない。未調整の株価と `AdjFactor` から自分で計算する(2.2)。調整の対象は分割・併合・株主割当増資で、配当は含まれない。
- **上場廃止銘柄**:データ保存期間内で上場していた日を指定すれば取得できる。
- **銘柄コード**:リクエストでは4桁も5桁も受け付ける(例:`27800` か `2780`)。英字を含むコード(例:`186A`)もある。
- **データの訂正**:J-Quants側で過去のデータが上書き訂正されることがある。訂正前の値はAPIから取れない。`AdjFactor` が訂正されたこともある(2026-10-13、株主割当増資の係数。未調整の値は変わっていない)。訂正は公式サイトの「Data Correction History and Known issues」ページに載る。

**銘柄コード**(公式FAQで確認済み)

- `Code` は5文字。5文字目は株式の種類を表すコードで、普通株は `0`。
- 内部IDとの変換:`TSE:7203` ↔ `72030`。英字を含むコードも同じ規則(`TSE:186A` ↔ `186A0`)。
- MVPでは、5文字目が `0` の銘柄(普通株)だけを扱う。

**Freeプランの制限**(公式仕様で確認済み)

| 項目 | 内容 |
|---|---|
| 株価四本値・銘柄一覧 | 2年分、12週間遅延 |
| 取引カレンダー(`/v2/markets/calendar`) | 12週間前〜2年12週間前 |
| リクエスト数 | **1分間に5回まで**(アカウント単位。APIキーを増やしても変わらない) |
| 制限を超えたとき | `429` が返る。`Retry-After` ヘッダーはないので、1分以上待ってから再開する。`429` になったリクエストも回数に数える。大きく超え続けると、約5分間すべてのリクエストがエラーになる |
| 期間外の日付を指定したとき | `400` が返り、取得できる範囲がメッセージに入る |
| CSVのダウンロード | 使えない(APIだけ) |

**銘柄一覧**(公式仕様で確認済み)

- `GET /v2/equities/master`。日付を指定しなければ、その日に上場している銘柄が返る。
- 主な項目:`Code`、`CoName`(銘柄名)、`CoNameEn`、`Mkt` / `MktNm`(市場区分)、`ProdCat`(商品区分)。
- 上場日・上場廃止日・上場廃止銘柄の一覧と、過去の売買単位は提供されない。

**要確認**(公式ドキュメントに記載がない。サインイン後にダウンロードできるサンプルデータか、実際のAPIで確認する)

- `AdjFactor` の小数の桁数(2.8の分数への戻し方と、相対誤差1e-4の基準が足りるか)
- 売買不成立の日のレコードに、`AdjFactor` と `ExRT` の値が入るか
- `ExRT` が1〜3以外の値をとるか。1日に複数の権利落ちが重なったときの表し方

### 3.2 利用規約から来る制約

- 取得したデータは `data/` に保存し、Gitで管理しない(`.gitignore` 済み)。
- データをリポジトリやアプリ経由で配布しない。公開デプロイしないのはこのため。
- 将来サブスク化するときは、商用利用と再配布が許されるデータソースに切り替える必要がある。

### 3.3 データソースを差し替えられる設計

データ取得はインターフェース(データソース)の裏に隠し、バックテストの計算部分はJ-Quantsを直接知らないようにする。データソースの責務は次の3つ。

1. 銘柄一覧を返す(銘柄ID、銘柄名、市場)
2. 銘柄IDと期間を受け取り、日足を返す。返すのは、日付、未調整の始値・高値・安値・終値・出来高、調整係数、権利落ちの種類。売買不成立の日もレコードを返し、価格はNullにする。
3. **銘柄ごとに**、取得できるデータの範囲(最初の日と最後の日)を返す

- 銘柄は「市場+コード」で一意に識別する(例:`TSE:7203`)。J-Quants固有のコード形式への変換は、データソースの中で行う。
- 取得したデータは共通の形式でParquetに保存し、計算エンジンにはこの共通形式だけを渡す。

**保存と更新のルール**

- 保存するのは未調整の値・調整係数・権利落ちの種類だけで、調整済み株価は保存しない。未調整の値は分割などで計算し直されることがない。
- ただし `AdjFactor` は後から訂正されることがある(3.1)。そのため、一定の日数(既定7日)ごとに、その銘柄の取得できる全期間を取り直す。
- 取り直したデータは保存済みのデータに合わせる:同じ日付は新しい値にし(訂正を反映する)、取得できる期間から外れた古い日付は残す(同じ条件のバックテストを後から再現できるようにするため)。
- 銘柄ごとに、データを取得した日時を保存する。

**取得のルール**

- リクエストは1分間に5回までに抑える(Freeプラン)。`429` が返ったら、1分以上待ってから再開する。
- 多くの銘柄の新しい日の分を取るときは、日付だけを指定して全銘柄をまとめて取得し、リクエスト数を節約する。

| 値幅制限 | MVPでは扱わない(「7. 既知の簡略化」を参照) |

### 3.5 株式分割・配当

- シグナル判定には、時点 t 基準の調整済み終値を使う(2.2)。t より後の分割の情報は使わない。
- 株数・資金・約定・評価額には未調整の株価を使い、分割・併合の日に持ち株数を変える(2.8)。
- 配当はMVPでは含めない。リターンは値動きだけで計算する。

### 3.6 上場廃止銘柄

- MVPの銘柄リストには、現時点で上場している銘柄だけを載せる。銘柄一覧を取得してあれば、一覧にない銘柄(上場廃止など)は API で実行できないようにする。
- 選べる銘柄は、どれも現在まで上場を続けた銘柄になる。そのため1銘柄ずつ実行しても、結果は楽観的になりやすい(生存者バイアス)。このことを結果画面や仕様書で隠さない。実データ(東証など)の結果には必ずこの注記を出す。架空データ(DEMO)は上場廃止のしくみを持たないので生存者バイアスの注記は出さず、代わりに「架空データです」と出す。
- J-Quantsは上場廃止銘柄も取得できる(3.1)。複数銘柄に広げる前に、廃止銘柄を銘柄リストに入れる方法と、上場廃止になったときに持っている株の扱いを決める(8章)。

### 3.7 データのチェック

計算の前に次をチェックし、満たさないときはデータの異常としてエラーにする。読み込む範囲(2.2)が同じなら、手数料・資金・持ち株の有無に関係なく、同じ結果(エラーか計算か)になるようにする(読み込む範囲は期間と `long_window` で決まる)。

- **入力全体**:日付が古い順に並んでいる(同じ日付が2回出てこない)。読み込む範囲の切り出し(2.2)がこれに頼るため。
- **読み込む範囲**(ウォームアップの最も古い有効日〜終了日)の各レコード:
  - 始値と終値は、どちらも Null か、どちらも Null でない
  - Null でない始値・終値は、0 より大きい有限の値
  - `AdjFactor` は Null でなく、0 より大きい有限の値
  - `AdjFactor ≠ 1` なら、`ExRT` は 1〜3 のどれか
  - `ExRT` が1か2で `AdjFactor ≠ 1` の日は、`AdjFactor` が 0.001〜1000 の範囲にあり、2.8 の方法で p/q に戻せる
- 読み込む範囲の外のレコードは計算に使わないので、チェックしない(1件の異常で、その銘柄のすべてのバックテストが止まらないようにするため)。
- 株数(2.7 で買う株数、2.8 の `shares × p`)が `int64_t` の範囲を超えるときも、エラーにする。

**チェックの順番**(誤りが2つ以上あるとき、どれを報告するか。C++ 版でも同じ順にする)

1. パラメータ:短期日数 → 長期日数(それぞれ、整数で1以上か → 1000以下か)→ 短期 < 長期 → 手数料率 → スリッページ率(それぞれ、数値か → 0以上か → 10%未満か)→ 初期資金(数値か → 1以上か → 10億以下か)
2. 開始日 > 終了日
3. 日付の順番(入力全体)
4. 期間内の営業日が3日未満
5. 読み込む範囲の各レコード(古い日から順に。1つのレコードの中では上の箇条書きの順)
6. 計算中の株数の桁あふれ

```
銘柄選択 → 戦略選択 → 詳細設定 → 実行 → 結果
```

| 画面 | 内容 |
|---|---|
| 銘柄選択 | 東証の銘柄を、コードまたは銘柄名で検索して1つ選ぶ |
| 戦略選択 | MVPでは「移動平均クロス」だけ |
| 詳細設定 | 期間(開始日・終了日)、短期日数、長期日数、手数料率(%)、スリッページ率(%)、初期資金(円) |
| 実行 | 入力チェックをしてから計算を始める |
| 結果 | 損益グラフ(日々の資産額)、成績表、資金不足で約定しなかった回数、ウォームアップに使った期間、データの取得日時 |

結果画面に表示する注記:

- 「最終日の資産額は、持っている株を売る手数料・スリッページを引く前の値です(清算コスト控除前)」(株を持ったまま期間が終わったとき)
- 「期間が1年未満のため、年率リターンは参考値です」(N < 年間の営業日数 のとき。短い期間を年率に換算すると、値が極端になるため)
- 「選べる銘柄は現在も上場している銘柄だけのため、結果は実際より良く見えやすくなります」(3.6)

### 4.1 ウォームアップに使った期間の表示

- 表示例:「ウォームアップに使った期間:2024-11-01〜2024-12-06(25営業日)」(営業日数は有効日の数)
- 開始日より前のデータが `long_window` 個に足りなかったときは、使えた範囲と営業日数を表示する。あわせて「開始日より前のデータが不足しているため、YYYY-MM-DD までシグナルを出していません」と表示する。日付は、シグナルを判定できる最初の有効日の**直前の営業日**(売買不成立の日のこともある)。期間内に一度も判定できないときは、期間の最後の営業日。
- 開始日より前のデータがまったくないときは「ウォームアップ期間:なし」と表示する。

| 項目 | デフォルト |

| 長期日数 | 25 |

### 4.3 入力チェック

エラーのときは実行せず、日本語のメッセージを表示する。

| 条件 | エラーメッセージ(例) |

| 短期日数 ≥ 長期日数 | 「短期の日数は長期の日数より小さくしてください」 |
| 日数が1未満、または整数でない | 「日数は1以上の整数で入力してください」 |

## 5. 成績表の指標

**評価価格と資産額**

- 期間内の営業日 t の評価価格は、t が有効日なら未調整の終値 `C(t)`。
- t が有効日でないときは、直近の有効日 u の終値を使い、`C(u) × (u の翌営業日から t までの、ExRT が1か2の日の AdjFactor の積)` とする。分割・併合で持ち株数が変わっても、評価額がずれないようにするため。 積は古い日から順に `1.0` に掛けていき、最後に `C(u)` に掛ける。
- 日ごとの資産額は `equity(t) = cash(t) + shares(t) × 評価価格(t)`。t = 0 は期間内の最初の営業日で、`equity(0)` は初期資金。
- 株を持っていない日(`shares(t) = 0`)は、評価価格を計算しない。期間の最初が売買不成立の日で、それより前に有効日がない場合でも、評価価格がないことでエラーにならないようにするため。

日次リターンは `r(t) = equity(t) / equity(t-1) − 1`(t = 1 … N)。N は日次リターンの数(期間内の営業日数 − 1)。入力チェック(4.3)により、N ≥ 2 になる。

| 指標 | 定義 |
|---|---|
| 総リターン | `equity(N) / 初期資金 − 1` |
| 年率リターン | `(equity(N) / 初期資金)^(年間の営業日数 / N) − 1`。N < 年間の営業日数 のときは参考値として注記する(4章)。結果が有限の値にならない(桁あふれ)ときは「算出不可」と表示する |
| 最大ドローダウン | `max over t of (1 − equity(t) / max_{s≤t} equity(s))`。正の割合で表示する(例:12.3%) |
| シャープレシオ | `mean(r) / std(r) × √年間の営業日数`。無リスク金利は0、`std` は標本標準偏差(ddof=1)。`std(r) = 0` のときは「算出不可」と表示する |
| 勝率 | 決済した取引(買い→売りの1往復)のうち、損益がプラス(> 0)だったものの割合。損益は手数料・スリッページを引いた後で判定する。損益0は負けに数える。決済した取引が0回のときは「−」と表示する |
| 取引回数 | 決済した取引(往復)の回数 |

1往復の損益:`((売りの notional − 売りの fee) + 端数を現金に換えた額の合計) − 買いの buy_cost`

端数を現金に換えた額の合計は、その取引のあいだに起きた分割・併合の `fraction_cash` を、古い順に 0.0 から足したもの(2.8)。

併合で持ち株が0株になって決済したとき(2.8)は、売りの項を0として計算する。

年間の営業日数は市場ごとの設定(3.4。東証は245日)で、計算エンジンにはパラメータとして渡す。

## 6. 正しさの前提(まとめ)

- **先読みバイアス**
  - シグナルは当日の終値で判定し、次の有効日の始値で約定する。
  - 移動平均は時点 t 基準の調整済み終値で計算し、t より後の価格も調整係数も使わない。
  - ウォームアップ期間は開始日より前のデータなので、使っても先読みにはならない。
  - 株数・資金の判定には未調整の株価を使う。
- **手数料・スリッページ**:必ずパラメータとして持ち、デフォルトは0にしない。
- **株式分割**:シグナルは時点 t 基準の調整済み株価、売買は未調整の株価で行い、分割・併合の日に持ち株数を変える。配当は含めない。
- **生存者バイアス**:上場廃止銘柄は対象外。結果が楽観的になりやすいことを明記する。
- **一致テスト**:Pythonリファレンス実装とC++ CPU版の結果が一致することを確認する(CUDA版はMVPに入れない)。
  - **完全に一致**すること:シグナルの日付、約定日、株数、資金不足の回数、取引回数、勝った取引の数、勝率。
  - **許容誤差内**であること:資産額と、勝率・取引回数以外の成績指標。基準は `|a − b| ≤ 1e-12 + 1e-9 × |b|`(a がC++、b がPython)。値が0付近でも判定できるように、絶対誤差と相対誤差を組み合わせる。
  - 移動平均の和は、どちらの実装も2.2の順番で足す。Pythonリファレンスでも `numpy.mean` などは使わず、ループで足す。`numpy` は内部で足す順番を変えるので、C++と結果がずれることがある。
  - 成績指標の計算の順番:日次リターンの平均は古い日から順に足して N で割る。標準偏差は `(r − 平均) × (r − 平均)` を古い日から順に足し、N − 1 で割ってから平方根をとる。シャープレシオは `(平均 / 標準偏差) × √年間の営業日数` の順に計算する。
  - シグナルの一覧には、検出したクロスをすべて載せ、2.4 の売買ルールで注文にしたか無視したかを付ける(C++版との一致はこの一覧全体で比べる)。
  - **C++のビルド設定**:`-ffp-contract=off` を付け、`-ffast-math` は使わない。CMakeで固定する。コンパイラが掛け算と足し算を1つの命令(FMA)にまとめたり、足す順番を変えたりすると丸め誤差が変わり、完全一致を求めている項目がずれるため。
  - テストには境界のケースを入れる:`D(t) = 0` になる日、権利落ち日に `D(t') = 0` になる日、株数がちょうど売買単位の境目になる資金、損益がほぼ0の取引、分割・併合の日(1:2、1:3、2:3、10:1)、併合で0株になる日、売買不成立の日。

## 7. 既知の簡略化

MVPでは次のことを扱わない、または理想化している。結果は現実の売買と違うことがある。

- **寄付きの成行注文**:寄付きの成行注文で、始値で約定できたと仮定する。株数も、まだ分からないはずの約定日の始値で決めている(2.7)。
- **ストップ高・ストップ安**:実際には約定できない日でも、始値で約定したものとして計算する。
- **株主割当増資**:持ち株数を変えず、割り当てられる権利の価値も受け取らない。そのため、権利落ち日に評価額が実際より下がる。
- **併合の端数**:実際には後日、売却代金として受け取るが、権利落ち日の評価価格(その日の終値)で現金に換えたとみなす。寄付き前の処理(2.5の手順1)なのに、その日の終値を使っている。ただし、この現金はその日の売買判断には使われないので、シグナルの先読みにはならない。
- **期間末の評価**:清算コスト控除前の値で評価する(2.9)。
- **単元未満株**:分割・併合で持ち株が売買単位の倍数でなくなっても(例:100株が1:1.5の分割で150株)、売りのシグナルでは全株を始値で売る。実際には単元未満株は市場で売れず、買取請求などの別の手続きになる。
- **配当**:含めない。
- **最低手数料・税金**:扱わない。
- **上場廃止銘柄**:対象外(3.6)。
